# Phase 9 Sprint 4 — Load-Test Report

ADR-027 Decision 3 (provisional MVP engineering targets) / Decision 6
(evidence-driven Horizon tuning) deliverable.

## Targets exercised

Per ADR-027 Decision 3, sized for the approved US initial launch market,
as provisional engineering constants — not a production demand forecast:

- Peak concurrent authenticated users: 250.
- Concurrent active auctions: 100.
- Peak concurrent bidders on a single auction: 25.
- Simultaneous bid submissions during a hot-auction closing window: 10/sec,
  sustained 60s.

## Tooling

`apps/web/app/Console/Commands/LoadTestPhase9.php` — seeds fixtures through
the real HTTP presence flow (start session → GPS ping → evidence photo)
rather than inserting `Auction`/`PresenceSession` rows directly, so
`LiveProximityChecker` sees genuine, verified presence state instead of
auto-cancelling auctions on first bid. Authenticates each simulated user
via the standard session-cookie + `XSRF-TOKEN` recipe over Guzzle's async
`Pool` (`GuzzleHttp\Promise\Utils::settle()->wait()`), giving real
concurrent HTTP load from a single CLI process. Options:
`--hot-bidders=25 --background-users=225 --background-auctions=99
--duration=60 --rate=10`, matching Decision 3's targets directly.

## Environment

Windows 11 host, Docker Desktop (WSL2 backend), 16 CPUs / ~16.6GB RAM
allocated to the Docker VM, source code bind-mounted from the Windows
filesystem into Linux containers. This is a development environment, not
a production-like Linux host — see "Environment caveat" below.

## Results by category

**1. Throughput/latency.** The full 900-request Decision-3-scale burst
completed with all correctness/domain-invariant behavior intact. Absolute
per-request latency was materially inflated by two environment-specific
causes (bind-mount overhead and PHP-FPM worker starvation, both below)
and does not represent a trustworthy production capacity figure — see
`docs/operations/synchronous-bottlenecks.md` for the full latency
diagnostic chain.

**2. Windows/Docker Desktop bind-mount overhead.** With
`opcache.validate_timestamps=On` (the dev default), even the trivial `/up`
endpoint measured 2.8–3.6s; with it temporarily set `Off`, the same
endpoint measured ~0.35–0.4s. This isolates a Windows↔Linux-VM filesystem
boundary `stat()` cost specific to Docker Desktop bind-mounts —
confirmed as an environment artifact, not a production-relevant finding,
since production would not bind-mount source this way. The change was
temporary and has been reverted; `opcache.validate_timestamps` is
confirmed back to `On`.

**3. Reverb behavior.** Reverb ran throughout the burst with no observed
disconnects or broadcast failures for the accepted-bid channel traffic
generated by the test.

**4. Horizon queue depth/wait time.** No backlog and no failed jobs were
observed for the achieved workload — see
`docs/operations/capacity-tuning-report.md` for the full Decision-6
process and conclusion (no configuration change made; none justified by
evidence).

**5. PostgreSQL contention/connections.** No deadlocks, lock timeouts, or
global contention observed. `pg_stat_activity` showed connection count
tracking PHP-FPM worker count 1:1 (2→8 connections across the burst, well
under `max_connections=100`), with no `idle in transaction` state
(no leaked transaction/session state).

**6. Synchronous bid-placement behavior.** `BidService`'s row-locked
transaction, `LiveProximityChecker` re-evaluation, and idempotency-ledger
claim all behaved correctly under concurrency — no double-accepted bids,
no lost updates, deterministic highest-bid ordering preserved throughout.

**7. Failed requests/invariant violations.** Zero domain-invariant
violations across the full burst. Failed HTTP requests observed during
early runs were traced to fixture/environment defects (fake
`presence_session_id` values triggering `LiveProximityChecker`
auto-cancellation; PHP-FPM worker starvation at the stock
`pm.max_children=5`; root-owned `700` evidence-photo storage directory)
— all three are fixed (see `docs/operations/synchronous-bottlenecks.md`);
none reflect an application-level domain defect.

## Environment caveat (required record per Sprint 4 approval)

- Decision 3's throughput targets were **not demonstrated** in this
  Windows/Docker Desktop environment — the latency measured here is not
  a valid basis for a production capacity claim in either direction.
- This load test **is** valid as correctness and domain-invariant
  validation: every business rule exercised (bid ordering, immutability,
  proximity-based auto-cancellation, idempotent retries, currency/seller/
  suspension checks) held under concurrent load.
- A production-like Linux environment validation remains an external
  launch-readiness requirement before any production capacity claim can
  be made. This is not resolved by Sprint 4 and is not scheduled by it.
